1 · Architecture

Four layers, one place that decides the outcome

The API layer only translates HTTP. AgentPipeline owns the run and is the only code that sets success, partial or failed. Every model call goes through one client that paces tokens and validates JSON.

2 · Agent workflow

Ten steps per request, in this order

Each step can stop the run with a clear reason. A typical run is 5 to 13 model calls.

  1. code · 0 tokens

    Screen

    Length limit, prompt-injection and unsafe keyword screens. Refused here → 400.

  2. LLM · 1 call

    Analyze + plan

    Type, category (record or planning), requested items, facts, missing info, assumptions, tasks. Not a document → 422.

  3. code (+1 re-plan)

    Validate plan

    2–6 tasks, known tools, no cycles, every requested item covered. One re-plan with the exact errors.

  4. LLM · 1 per section

    Execute tasks

    Dependency order. A task gets its prerequisites' checked content.

  5. code

    Ground

    A record must appear in the request. An unsupported owner, date or value becomes "To be confirmed".

  6. code

    Completeness

    A requested section with no source facts is marked; a required one with nothing supported fails.

  7. LLM · chunked

    Review

    Unsupported facts, missing items, unlabelled proposals, contradictions, wrong heading.

  8. LLM · ≤3 sections

    Repair + verify

    Rewrite with the issues, re-ground in code, review again. Unresolved in a required section → fail.

  9. code

    Dedupe + final gate

    A repeated record stays where its type belongs. Every item covered, every proposal labelled.

  10. code

    Render

    Build the Word file, save atomically, reopen and check the headings. Return the link.

3 · The parts in detail

Planning, LLM, tools, documents, API

Planning logic

The model plans, code validates

  • One analyze call returns the request's structure and a task list. Each task names a tool, a heading, its dependencies and the requested items it covers.
  • Code checks: 2–6 tasks, known tools, unique IDs, dependencies exist, no cycles, every requested item covered.
  • Invalid → one re-plan with the exact errors. Still too long → code merges neighbouring same-tool tasks that don't depend on each other.
  • A planned "Assumptions" task is folded into the automatic Assumptions section, so it never appears twice.
  • Required is set by code: a task is required only if it covers a requested item.

Why: the agent picks its own plan, but a bad plan never reaches the writing step.

LLM integration

One client, strict JSON, hard budgets

  • Groq SDK, openai/gpt-oss-120b (20b as a drop-in fallback). JSON mode plus the Pydantic schema in the prompt.
  • Every reply is parsed into a strict model (extra="forbid"). Invalid or cut-off JSON is retried at most twice, with the validation error as feedback.
  • The request is passed only inside <request> tags, as data.
  • Process-wide TokenPacer books tokens ahead of each call to stay under Groq's 8K tokens/min. 429s honour retry-after, at most 3 waits; a daily-limit 429 stops the request at once.
  • An over-cap call is never sent, and a "too large" error is never resent.

Tool usage

Two tools the planner chooses from

ToolProducesUsed for
write_sectionParagraphs + typed bullet itemsSummary, decisions, risks, phases
build_tableRows with owner, due, valueAction items, schedule, budget
  • Each tool has its own output schema and a converter into a common Section.
  • The planner picks a tool by name for every task; an unknown tool makes the plan invalid.
  • Repair rewrites a section with the same tool it was written with.

Why only two: fewer choices for a small model, and every tool output is something code can check.

Document generation

Records vs proposals, then python-docx

  • Every item is a record (a fact from the request) or a proposal (the agent's suggestion).
  • A proposal must carry a visible label: Proposed, Recommended, Potential or Illustrative. A guess cites an assumption, e.g. "Assumption A1".
  • An automatic Assumptions section lists what the agent assumed, so nothing invented is hidden.
  • The renderer writes the title, headings, bullets and tables, hides unused table columns, and hides a value that only repeats the owner.
  • Saved atomically, reopened to verify the headings, served only by names the agent created.

Why: the LLM only ever returns JSON text; the file itself is built locally by code.

Guardrails

Four layers, all enforced in code

  • Input: length and keyword screens before any token is spent.
  • Plan: validation and one re-plan before any section is written.
  • Grounding: records must quote the request; unknown assumption IDs are stripped.
  • Final gate: every requested item covered, every proposal labelled, no placeholders in required sections. Any failure means no document.

Rule I kept: judgement goes in prompts, checkable rules go in code with tests. I never loosened a check or a limit to make a run pass.
